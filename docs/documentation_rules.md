# 연구 문서 분리 규칙

- 시행일: 2026-09-03
- 적용 범위: 시행일 이후 작성하거나 갱신하는 프로젝트 연구·진행 문서
- 기준 문서: 이 파일을 문서 분류와 작성 방식의 source of truth로 사용한다.

## 1. 기본 원칙

모든 기록을 **공유용**과 **개인·내부용**으로 명확하게 분리한다.

- 공유용은 팀원 또는 외부 연구 협력자에게 그대로 전달할 수 있는 연구 문서다.
- 내부용은 연구 재현, 판단 추적과 개인 작업 인계를 위한 상세 원장이다.
- 연구 내용이나 연구 진행 상태가 바뀌는 작업은 두 문서를 한 쌍으로 작성한다.
- 내부용을 먼저 사실대로 기록하고, 공유 가능한 연구 내용만 추출해 공유용을 작성한다.
- 한 파일에 공유용과 내부용 내용을 섞지 않는다.

## 2. 저장 위치와 파일명

```text
docs/
├─ shared/       팀 공유 가능 문서
├─ internal/     개인·내부 상세 기록
└─ templates/    문서 유형별 템플릿
```

파일명 규칙:

```text
docs/shared/YYYY-MM-DD_<topic>_shared.md
docs/internal/YYYY-MM-DD_<topic>_internal.md
```

한 쌍의 문서는 같은 날짜와 `<topic>`을 사용하고, 문서 머리말에 동일한 `문서 ID`를 기록한다.

```text
문서 ID: DOC-YYYYMMDD-<topic>-R<revision>
```

예시:

```text
docs/shared/2026-09-03_sensor_selection_shared.md
docs/internal/2026-09-03_sensor_selection_internal.md
문서 ID: DOC-20260903-sensor-selection-R1
```

## 3. 공유용 문서 규칙

### 3.1 작성 가능한 내용

공유용에는 다음의 **연구 내용과 연구 진행 내용만** 작성한다.

1. 연구 배경, 문제 정의와 연구 질문
2. 검증할 가설과 연구 범위
3. 모델, 데이터, 센서와 평가 방법의 연구상 설명
4. 계획, 진행 중, 완료, 중단 또는 미채택 등 연구 진행 상태
5. 검증된 정량·정성 결과와 negative result
6. 결과의 연구적 해석, 한계와 주장 가능한 범위
7. 다음 연구 실험과 선행 관계
8. 내용을 뒷받침하는 논문과 공개 연구자료

예비 결과를 공유해야 한다면 반드시 `예비`, `미검증` 또는 `진행 중`으로 표시한다. 확정 결과와
예비 결과를 같은 표현으로 쓰지 않는다.

### 3.2 작성하면 안 되는 내용

다음 내용은 공유용에 넣지 않는다.

- 사용자명, 로컬 절대경로, 서버 주소와 장비 식별정보
- 실행 명령어, shell 출력, 전체 stack trace와 디버깅 로그
- 패키지 설치, 환경 설정과 파일 복구 과정
- 내부 파일 inventory, checkpoint 위치와 세부 hash 목록
- 개인 메모, 대화 기록, 감상과 추측
- 담당자 배정, 개인 일정, 회의 운영과 비용·구매 처리
- 접근 권한, 비공개 데이터 입수 경로와 내부 관리 절차
- 연구 결과와 무관한 코드 정리 또는 행정 작업
- 결과를 설명하는 데 필요하지 않은 시행착오
- 비밀번호, API key, token, 개인정보와 기타 secret

공유용에 구현 파일을 연결할 필요가 있을 때도 연구 이해에 필수인 공개 상대경로만 최소한으로
사용한다. 로컬 절대경로나 내부 저장 위치는 사용하지 않는다.

### 3.3 공유용 상태 표현

다음 상태를 일관되게 사용한다.

| 상태 | 의미 |
| --- | --- |
| `planned` | 연구 질문과 실험 계획만 확정됨 |
| `in_progress` | 데이터 수집, 구현 또는 실험이 진행 중임 |
| `completed` | 사전 정의한 실험과 검증이 완료됨 |
| `paused` | 근거가 명시된 상태로 일시 중단됨 |
| `not_selected` | 실험은 완료했으나 채택 기준을 통과하지 못함 |

`implemented`와 `validated`, `selected`는 같은 뜻이 아니다. 구현만 완료한 항목을 검증 또는 채택된
연구 결과처럼 표현하지 않는다.

## 4. 개인·내부용 문서 규칙

내부용은 해당 작업을 나중에 재현하거나 판단을 감사할 수 있도록 가능한 한 상세하게 기록한다.

필수 기록 항목:

1. 요청 내용, 작업 범위, 시작 시각과 전제
2. 작업 전 상태와 확인한 자료
3. 수정·생성·삭제한 파일과 구체적인 변경 내용
4. 사용한 명령어, config, seed, split과 실행 환경
5. 데이터, checkpoint, code revision과 provenance
6. 원본 metric, 로그, 산출물과 검증 결과
7. 선택한 방법, 비교 대안과 선택 이유
8. 실패, 오류, 중단 원인, 우회 방법과 미채택 실험
9. 임시 가정, 불확실한 부분과 확인이 필요한 사실
10. 데이터 license, 접근 상태와 비식별화 관련 판단
11. 남은 작업, 위험, 다음 실행의 정확한 시작점
12. 공유용에 반영한 내용과 제외한 내용

내부용은 상세 기록이지만 다음 정보는 기록하지 않는다.

- 비밀번호, API key, access token과 private key
- 원문 보존이 허용되지 않은 개인정보
- 동의 범위를 벗어난 원본 음성·영상 또는 식별정보

필요한 경우 secret의 실제 값 대신 `환경변수 이름`, `보관 시스템`과 `접근 필요 여부`만 기록한다.

## 5. 작성 절차

연구 변경이 있는 작업은 아래 순서를 따른다.

1. 작업 시작 시 문서 ID와 공유·내부 파일명을 정한다.
2. 내부용에 요청, 가정과 작업 전 상태를 기록한다.
3. 구현·실험 중 명령, 실패, 결정과 결과를 내부용에 누적한다.
4. 결과 파일과 metric을 원본 산출물에서 다시 확인한다.
5. 내부용의 확인된 내용 중 공유 허용 목록만 공유용에 옮긴다.
6. 공유용의 모든 숫자와 상태가 내부 evidence와 대응하는지 확인한다.
7. 공유용에서 금지 항목과 내부 경로가 제거됐는지 검사한다.
8. 두 문서의 날짜, 문서 ID, revision과 연구 상태를 맞춘다.
9. 작업 보고 시 공유용과 내부용 경로를 각각 명시한다.

연구 내용이나 진행 상태가 바뀌지 않은 관리·환경·복구·디버깅 작업은 내부용만 갱신한다. 이때
내부용에 다음처럼 이유를 기록한다.

```text
shared_update: none
reason: 연구 내용 또는 연구 진행 상태의 변화가 없는 내부 작업
```

## 6. 결과와 근거의 대응

- 공유용의 모든 수치에는 내부용의 원본 metric, 결과 파일 또는 검증 기록이 있어야 한다.
- 원본을 다시 확인하지 못한 과거 수치는 `기존 기록 기준`이라고 표시한다.
- 결과 확인 후 바꾼 threshold나 규칙은 post-hoc임을 내부용과 공유용 모두에서 밝힌다.
- 실패 결과와 `not_selected` 결정도 연구 진행에 해당하면 공유용에 연구적 의미만 기록한다.
- 명령, stack trace와 실패 복구 과정은 내부용에만 기록한다.
- 내부용이 source of truth이며 공유용은 내부용에서 승인된 연구 내용만 추출한 문서다.

## 7. 문서 갱신 단위

- 하나의 연구 질문 또는 실험 묶음을 하나의 `<topic>`으로 사용한다.
- 같은 연구 질문의 보완은 revision을 올리고 기존 결론의 변경 이유를 내부용에 남긴다.
- 연구 질문이 달라지면 새 문서 쌍을 만든다.
- 공유용은 현재 연구 상태가 잘 보이도록 간결하게 유지한다.
- 내부용은 이전 실패와 판단을 삭제하지 않고 시간순으로 누적한다.
- 과거 결과를 새 결과로 덮어쓰지 말고 superseded 관계를 기록한다.

## 8. 공개 전 점검표

### 공유용

- [ ] 연구 내용과 연구 진행 이외의 내용이 없는가?
- [ ] 로컬 경로, 명령어, 로그, 환경·복구 기록이 없는가?
- [ ] 수치와 상태가 내부 evidence와 일치하는가?
- [ ] 예비 결과와 확정 결과가 구분되는가?
- [ ] 실패와 한계가 과장 없이 연구적 의미로 기록됐는가?
- [ ] 개인정보, 음성 원문과 secret이 없는가?

### 개인·내부용

- [ ] 실행 조건과 변경 파일을 재현 가능한 수준으로 기록했는가?
- [ ] 실패, 대안과 판단 이유를 생략하지 않았는가?
- [ ] 원본 metric과 provenance를 기록했는가?
- [ ] 공유 반영·제외 항목을 기록했는가?
- [ ] 실제 secret이나 허가되지 않은 개인정보가 없는가?

## 9. 기존 문서 처리

이 규칙 시행 전에 작성된 통합 문서는 즉시 삭제하거나 이동하지 않는다. 공유 내용과 내부 내용이
섞여 있으면 상단에 `legacy internal` 표시를 추가하고 내부 참고용으로만 사용한다. 이후 외부 또는
팀 공유가 필요하면 해당 문서에서 연구 내용과 진행 내용만 추출해 `docs/shared/`에 새 문서를 만든다.
